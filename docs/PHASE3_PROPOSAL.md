# مقترح المرحلة 3 — المحرك المحاسبي: القيود اليومية والأستاذ العام

**الحالة:** النسخة النهائية للمراجعة — القرارات التسعة **معتمدة** (2026-11-10) مع الملاحظات الإضافية، ومحدّثة بالنقاط الأربع للمراجعة الثانية (القيد العكسي وحسابات المراقبة، التحقق العشري، حالات الفترات، مصفوفة الحماية) والنقاط الخمس للمراجعة الثالثة (NULL وصيغة الصفر، اكتمال العكسي، ذرية P2، إعدادات السلاسل، اختبار التزامن) — **لم يبدأ التنفيذ.** النقاط التي تحتاج قراركم في القسم 16.
**الأساس:** الإصدار 0.3.1 (commit `4dd1d3f`) · **الإصدار المستهدف:** 0.4.0

## 1. الهدف والنطاق

بناء القلب المحاسبي الذي ستبني عليه كل المراحل التالية: **قيد يومي يُرحَّل إلى أستاذ عام لا يُعدَّل**، عبر **محرك ترحيل واحد** ستستخدمه لاحقًا الفواتير والتحصيلات والمخزون دون تكرار قواعد الترحيل.

**داخل المرحلة:** ترقيم المستندات · سياسة الترحيل في دليل الحسابات · محرك الترحيل والأستاذ العام (بالعملة على مستوى السطر) · القيد اليومي (مسودة ← ترحيل) · القيد العكسي · القيد الافتتاحي · ضوابط الفترات والسنوات · ثلاثة تقارير فقط: **دفتر اليومية، كشف الحساب، ميزان المراجعة**.

**خارج المرحلة** (القسم 13): العملاء والموردون، التحصيل والسداد، الفواتير، المخزون، **الإقفال السنوي** (المرحلة 4، والمحرك جاهز له من الآن)، حساب فروق العملة الآلي، القوائم المالية.

## 2. القرارات المعتمدة

| # | القرار | الصيغة المعتمدة | ما يلزم التنفيذ به |

| 9 | القوائم المالية | مؤجلة لمرحلة التقارير | تقارير المرحلة 3: دفتر اليومية، كشف الحساب، ميزان المراجعة فقط |

### 5.1 العلاقات

```
branches, fiscal_years/periods, currencies, exchange_rates, accounts, cost_centers   (قائمة)
        ▲            ▲                ▲           ▲
        │            │                │           │ rate_id (لقطة للتتبع)
document_series ──► document_counters │           │
        │                             │           │
        └──► issued_numbers ◄── number ── journal_entries ──1:N──► journal_lines ──► accounts, cost_centers,
                                          │   ▲                                       currencies, exchange_rates
                                          │   └── reverses_id (1:1، فريد)
                                          │ عند الترحيل (معاملة واحدة)
                                          ▼
                                     gl_entries  ──► accounts, cost_centers, branches, fiscal_periods,
                                   (الأستاذ العام)    fiscal_years, currencies
```
**لماذا `journal_lines` و`gl_entries` معًا؟** القيد اليومي مستند واحد من مستندات كثيرة قادمة؛ الفاتورة لها سطور أصناف لا سطور قيد. الأستاذ هو المكان الموحد الذي تُرحَّل إليه كل المستندات وتقرأ منه كل التقارير.

  id INTEGER PRIMARY KEY,
  code         TEXT NOT NULL UNIQUE,          -- JV, RV, OB  (يُقفل بعد أول رقم)

  name_ar TEXT NOT NULL, name_en TEXT NOT NULL,       -- تسميات فقط: قابلة للتعديل دائمًا

  per_branch   INTEGER NOT NULL DEFAULT 1 CHECK (per_branch IN (0, 1)),     -- (يُقفل)
  reset_yearly INTEGER NOT NULL DEFAULT 1 CHECK (reset_yearly IN (0, 1)),   -- (يُقفل)
  padding      INTEGER NOT NULL DEFAULT 6 CHECK (padding BETWEEN 4 AND 10), -- (يُقفل)
  is_default   INTEGER NOT NULL DEFAULT 0 CHECK (is_default IN (0, 1)),     -- فهرس فريد جزئي لكل doc_type

document_counters (
  series_id  INTEGER NOT NULL → document_series,
  branch_key INTEGER NOT NULL,                -- branch_id، أو 0 إن لم تكن السلسلة لكل فرع
  year_key   INTEGER NOT NULL,                -- [منفّذ 3.1] سنة بداية السنة المالية (مقطع FY2026)، أو 0 إن لم تكن تُعاد سنويًا
  last_value INTEGER NOT NULL CHECK (last_value >= 1),
  PRIMARY KEY (series_id, branch_key, year_key))
  -- triggers: الإضافة بـ last_value = 1 فقط؛ التعديل last_value = OLD.last_value + 1 فقط ولا يغيّر المفتاح؛ لا حذف

issued_numbers (                              -- سجل الأرقام الصادرة: إضافة فقط
  id INTEGER PRIMARY KEY,
  series_id INTEGER NOT NULL → document_series, branch_key INTEGER NOT NULL, year_key INTEGER NOT NULL,
  seq       INTEGER NOT NULL CHECK (seq >= 1),
  number    TEXT NOT NULL UNIQUE,             -- فريد على مستوى كل المستندات وكل السلاسل
  doc_type  TEXT NOT NULL, source_id INTEGER NOT NULL,

### 5.4 `journal`

```sql
journal_entries (
  id INTEGER PRIMARY KEY,
  branch_id           INTEGER NOT NULL → branches,
  entry_type          TEXT NOT NULL CHECK (entry_type IN ('general', 'opening', 'reversal', 'closing')),  -- closing محجوز
  status              TEXT NOT NULL CHECK (status IN ('draft', 'posted')),
  entry_date          TEXT NOT NULL CHECK (date(entry_date) IS entry_date),
  series_id           INTEGER NOT NULL → document_series,
  default_currency_id INTEGER NOT NULL → currencies,     -- افتراضي للسطور فقط
  description         TEXT NOT NULL,
  reference           TEXT,                              -- اختياري
  total_base          TEXT NOT NULL DEFAULT '0',         -- '0' في المسودة؛ يُحسب عند الترحيل
  is_multi_currency   INTEGER NOT NULL DEFAULT 0 CHECK (is_multi_currency IN (0, 1)),
  future_date_confirmed INTEGER NOT NULL DEFAULT 0 CHECK (future_date_confirmed IN (0, 1)),
  created_by INTEGER NOT NULL, created_at TEXT NOT NULL, updated_by INTEGER NOT NULL, updated_at TEXT NOT NULL,
  -- إلزامية حسب الحالة (NULL مقصود في المسودة أو لغير العكسي):
  number           TEXT UNIQUE,             fiscal_period_id INTEGER → fiscal_periods,
  decimal_snapshot TEXT,                    posted_by INTEGER, posted_at TEXT,
  reverses_id      INTEGER → journal_entries, reason TEXT,
  CHECK ((status = 'posted') = (number IS NOT NULL)),
  CHECK ((status = 'posted') = (fiscal_period_id IS NOT NULL)),
  CHECK ((status = 'posted') = (decimal_snapshot IS NOT NULL)),
  CHECK ((status = 'posted') = (posted_by IS NOT NULL AND posted_at IS NOT NULL)),
  CHECK (status = 'draft' OR <canonical_positive(total_base, 8)>),
  CHECK (total_base = '0' OR <canonical_positive(total_base, 8)>),
  CHECK ((entry_type = 'reversal') = (reverses_id IS NOT NULL)),
  CHECK ((entry_type = 'reversal') = (reason IS NOT NULL)),
  CHECK (reason IS NULL OR length(trim(reason)) BETWEEN 3 AND 500))
-- فهرس فريد جزئي: القيد يُعكس مرة واحدة بين القيود المرحّلة
CREATE UNIQUE INDEX journal_one_reversal ON journal_entries (reverses_id) WHERE status = 'posted';

journal_lines (
  id INTEGER PRIMARY KEY,
  entry_id      INTEGER NOT NULL → journal_entries ON DELETE CASCADE,
  line_no       INTEGER NOT NULL CHECK (line_no >= 1),
  account_id    INTEGER NOT NULL → accounts,
  currency_id   INTEGER NOT NULL → currencies,
  rate          TEXT NOT NULL,                  -- لقطة: '1' للعملة الأساسية
  rate_source   TEXT NOT NULL CHECK (rate_source IN ('base', 'table', 'manual')),
  debit_fc      TEXT NOT NULL DEFAULT '0', credit_fc TEXT NOT NULL DEFAULT '0',   -- المبلغ الأصلي
  debit         TEXT NOT NULL DEFAULT '0', credit    TEXT NOT NULL DEFAULT '0',   -- بالعملة الأساسية: '0' في المسودة
  -- اختيارية أو إلزامية حسب الحالة:
  cost_center_id   INTEGER → cost_centers,      -- حسب سياسة الحساب (trigger الترحيل)
  description      TEXT,
  reverses_line_id INTEGER → journal_lines,     -- إلزامي في سطور القيد العكسي فقط (trigger)
  rate_id          INTEGER → exchange_rates,    -- إلزامي لـ table
  table_rate TEXT, rate_reason TEXT, rate_set_by INTEGER, rate_set_at TEXT,       -- إلزامية لـ manual
  UNIQUE (entry_id, line_no),
  UNIQUE (entry_id, reverses_line_id),          -- لا يتكرر سطر الأصل داخل العكسي
  -- الصيغ (القسم 5.5): '0' أو موجب قانوني فقط
  CHECK (debit_fc  = '0' OR <canonical_positive(debit_fc, 8)>),
  CHECK (credit_fc = '0' OR <canonical_positive(credit_fc, 8)>),
  CHECK (debit     = '0' OR <canonical_positive(debit, 8)>),
  CHECK (credit    = '0' OR <canonical_positive(credit, 8)>),
  CHECK (<canonical_positive(rate, 12)>),
  CHECK (table_rate IS NULL OR <canonical_positive(table_rate, 12)>),
  -- طرف واحد بالضبط في المبلغ الأصلي
  CHECK ((debit_fc = '0') <> (credit_fc = '0')),
  -- المبلغ الأساسي: إما لم يُحسب بعد (الاثنان '0') أو في الطرف نفسه للمبلغ الأصلي
  CHECK ((debit = '0' AND credit = '0') OR ((debit = '0') = (debit_fc = '0') AND (credit = '0') = (credit_fc = '0'))),
  -- اتساق مصدر السعر (بصيغة IS الآمنة من NULL)
  CHECK ((rate_source = 'base') = (rate = '1' AND rate_id IS NULL AND table_rate IS NULL)),
  CHECK ((rate_source = 'table') = (rate_id IS NOT NULL)),
  CHECK ((rate_source = 'manual') = (rate_reason IS NOT NULL AND rate_set_by IS NOT NULL AND rate_set_at IS NOT NULL)),
  CHECK (rate_reason IS NULL OR length(trim(rate_reason)) BETWEEN 3 AND 500))

gl_entries (                                    -- الأستاذ العام: إضافة فقط
  id INTEGER PRIMARY KEY,
  source_type TEXT NOT NULL, source_id INTEGER NOT NULL, doc_number TEXT NOT NULL,
  entry_kind  TEXT NOT NULL CHECK (entry_kind IN ('normal', 'opening', 'closing')),
  posting_date TEXT NOT NULL CHECK (date(posting_date) IS posting_date),
  fiscal_period_id INTEGER NOT NULL, fiscal_year_id INTEGER NOT NULL, branch_id INTEGER NOT NULL,
  account_id INTEGER NOT NULL, currency_id INTEGER NOT NULL,
  rate TEXT NOT NULL, rate_source TEXT NOT NULL CHECK (rate_source IN ('base', 'table', 'manual')),
  debit_fc TEXT NOT NULL, credit_fc TEXT NOT NULL,      -- المبلغ الأصلي
  debit    TEXT NOT NULL, credit    TEXT NOT NULL,      -- بالعملة الأساسية (ما تقرؤه التقارير)
  posted_by INTEGER NOT NULL, posted_at TEXT NOT NULL,
  source_line_id INTEGER,                        -- اختياري: مستندات قادمة قد تجمع أكثر من سطر
  cost_center_id INTEGER,                        -- اختياري حسب سياسة الحساب
  description TEXT,
  -- نفس قيود الصيغة، والطرف الواحد في الأصلي والأساسي معًا، والأساسي غير صفري:
  CHECK ((debit_fc = '0') <> (credit_fc = '0')),
  CHECK ((debit = '0') <> (credit = '0')),
  CHECK ((debit = '0') = (debit_fc = '0')))
```

### 5.5 NULL وصيغة الصفر (مراجعة 3، النقطة 1)

**لماذا لا يكفي `CHECK` وحده:** في SQL، `CHECK` الذي يُقيَّم إلى NULL **يمر**. جرّبت ذلك في قاعدة مؤقتة أثناء إعداد هذه النسخة على الصياغة السابقة للمقترح:
- سطر `debit_fc = NULL, credit_fc = '5'` **قُبل** (`(NULL = '0') <> ('5' = '0')` = NULL ⇒ يمر).
- سطر `debit_fc = '0.0', credit_fc = '0'` **قُبل**: صفر في الطرفين تجاوز شرط الطرف الواحد لأن `'0.0' ≠ '0'` نصيًا.

بالصياغة الجديدة أعلاه رُفضت كل هذه الحالات في التجربة نفسها: NULL، `'0.0'`، `'00'`، `'-0'`، `'0'` في الطرفين، القيمة في الطرفين، و`0` رقمًا (STRICT ترفض غير النص).

**القواعد:**
1. **كل حقل إلزامي دائمًا** ⇒ `NOT NULL` صريح (منها `rate_source`، `rate`، المبالغ الأربعة، `currency_id`، `account_id`، `status`، `entry_type`، `entry_kind`، وكل أعمدة الأستاذ عدا الثلاثة الاختيارية).
2. **الحقول الإلزامية حسب الحالة** (`number`، `fiscal_period_id`، `decimal_snapshot`، `posted_by/at` للمرحّل؛ `reverses_id` و`reason` للعكسي؛ `rate_id` لـ table؛ حقول السعر اليدوي لـ manual؛ `reverses_line_id` لسطور العكسي) لا يمكن أن تكون `NOT NULL` لأنها فارغة شرعًا في حالة أخرى. تُفرض بـ:
   - `CHECK` بصيغة **تكافؤ** يقارن نتيجتي `IS NULL`/`IS NOT NULL` (لا تعطي NULL أبدًا) مع عمود `NOT NULL` (`status`، `entry_type`، `rate_source`) ⇒ لا مجال لمرور NULL؛
   - وtrigger الترحيل يعيد فحصها عند `draft → posted`.
3. **الصفر بصيغة واحدة `'0'` فقط:** كل مبلغ إما `'0'` حرفيًا أو يطابق نمط الموجب القانوني (القسم 6.9) — والنمط لا يقبل أي صفر (`'0.0'`، `'0.00'`، `'00'`، `'-0'`، `'+0'`، `' 0'`، `'0.'`). إذن **«غير `'0'`» تعني «موجب» حتمًا**، فيصبح شرط الطرف الواحد `(debit_fc = '0') <> (credit_fc = '0')` دقيقًا ولا يمكن تجاوزه بصيغة صفر بديلة أو NULL.
4. **المحرك:** `decimal.commit`/`toStorage` تنتج الشكل القانوني (الصفر = `'0'` دائمًا)، و`fromStorage` ترفض غير القانوني. عند الترحيل يعيد المحرك قراءة كل قيمة ويحكم على الطرف بـ `decimal.isZero` على **القيمة** لا على النص، ثم يتأكد أن النص المخزن هو الشكل القانوني نفسه — فأي `'0.0'` دخل بتجاوز `CHECK` (PRAGMA) يُرفض `CORRUPT_VALUE`.
5. **المبالغ الأساسية في المسودة `'0'`** (بدل NULL). عند الترحيل يجب أن يكون الأساسي غير صفري في طرف المبلغ الأصلي نفسه؛ وإلا يُرفض الترحيل `BASE_AMOUNT_ZERO` (حالة سطر أجنبي صغير جدًا يصبح صفرًا بعد التحويل — انظر القسم 16، النقطة 3).

**الحماية داخل القاعدة:** القائمة الكاملة لكل قاعدة وأين تُفرض في **مصفوفة الحماية (القسم 9)**. باختصار:
- `journal_entries`: لا تعديل ولا حذف لقيد مرحّل؛ الانتقال الوحيد `draft → posted` مرة واحدة؛ وعند هذا الانتقال trigger يتحقق من الاتزان والفترة والحسابات (القسم 9).
- `journal_lines`: لا إضافة ولا تعديل ولا حذف لسطور قيد مرحّل.
- `gl_entries`، `issued_numbers`: لا تعديل ولا حذف إطلاقًا.
- حذف المسودة مسموح (لا رقم لها ولا أثر في الأستاذ) بحدث تدقيق.

**الفهارس:** `gl_entries (account_id, posting_date)`، `(branch_id, posting_date)`، `(cost_center_id, posting_date)`، `(source_type, source_id)`، `(fiscal_year_id, entry_kind)`؛ `journal_entries (status, entry_date)`، `(branch_id, entry_date)`.

## 6. قواعد العمل

### 6.1 دورة القيد
`مسودة` (تُعدَّل وتُحذف، بلا رقم) ← `ترحيل` (رقم + أستاذ + قفل نهائي) ← عند الخطأ: `قيد عكسي` مرتبط بسبب، ثم قيد صحيح جديد.
**فصل المهام:** إعداد `journalSegregatePosting` (افتراضي معطل): عند تفعيله يُرفض ترحيل المستخدم لقيد أنشأه أو عدّله آخر مرة.

### 6.2 قواعد الترحيل (محرك واحد لكل المستندات)
معاملة واحدة `BEGIN IMMEDIATE` تشمل: التحقق، إصدار الرقم، المبالغ الأساسية، تحديث القيد، الأستاذ، التدقيق. أي فشل ⇒ لا شيء يُحفظ ولا رقم يُستهلك.
1. سطران على الأقل؛ كل سطر طرف واحد بمبلغ أصلي موجب معتمد بسياسة عملة السطر.
2. الحساب تفصيلي نشط؛ ويقبل القيد اليدوي/الافتتاحي (`allow_manual_entry`). **القيد العكسي معفى من «نشط» و`allow_manual_entry` وسياسة مركز التكلفة فقط، وبشروط القسم 6.5.**
3. مركز التكلفة حسب سياسة الحساب، نشط، تفصيلي، وفرعه (إن وُجد) = فرع القيد.
   كل مبلغ وسعر يُعاد التحقق منه بالمحرك العشري من القيمة المخزنة نفسها (القسم 6.9).
4. الفرع ضمن نطاق المستخدم ونشط.
5. التاريخ في فترة **مفتوحة**؛ وضوابط القسم 7.
6. العملة نشطة؛ سعر السطر لقطة من الجدول، أو يدوي بشروط 6.3.
7. **الاتزان بالعملة الأساسية بالضبط** (6.4)؛ وإن كان القيد بعملة واحدة: الاتزان بها أيضًا.
8. فصل المهام إن كان مفعّلًا.

### 6.3 السعر اليدوي
- يُحدَّد في السطر بالسعر والسبب؛ **الخادم** يتحقق من `journal.override_rate` للمستخدم عند الحفظ، ويحفظ `rate_set_by` و`rate_set_at` و`table_rate` (سعر الجدول في تاريخ القيد إن وُجد).
- عند الترحيل: يتحقق الخادم مجددًا أن **المرحِّل** يملك `journal.override_rate` إن احتوى القيد سعرًا يدويًا (الترحيل هو ما يجعل السعر نافذًا).
- التدقيق: حدث `journal.rate_overridden` لكل سطر عند الحفظ (المستخدم، التوقيت، السعر، المصدر، سعر الجدول، السبب)، وتفاصيل السعر ضمن حدث `journal.posted`.
- تغيير تاريخ المسودة أو عملة السطر يُسقط السعر اليدوي ويعيد السعر من الجدول (لا يبقى سعر يدوي لتاريخ لم يُبرَّر له).

### 6.4 العملة على مستوى السطر — الاتزان الدقيق
1. السطور تُجمَّع حسب **(العملة، السعر، الطرف)**. لكل مجموعة: المجموع الأصلي يُحوَّل **مرة واحدة** `convert(total, rate)` بسياسة العملة الأساسية، ثم يُوزَّع على سطورها بأوزان مبالغها بـ `allocate` (أكبر الباقي، حتمي).
2. القيد بعملة واحدة وسعر واحد: مجموع المدين الأصلي = الدائن ⇒ المبلغان الأساسيان متساويان **بالبناء**، بلا فروق تقريب.
3. القيد متعدد العملات أو الأسعار: الشرط الوحيد = مجموع المدين الأساسي = مجموع الدائن الأساسي **بالضبط**. إن اختلفا يرفض الخادم الترحيل ويعرض الفرق، ولا يُضاف أي سطر آليًا؛ يضيف المستخدم سطرًا صريحًا (فرق عملة/عمولة) بحساب يختاره.
4. المبالغ الأساسية تُحسب **مرة واحدة عند الترحيل** وتُحفظ؛ لا تقرير ولا عكس ولا تغيير سياسة يعيد حسابها.

**مثال 1 (أرقام فعلية من المحرك):** قيد بالدولار بسعر 48.123456789012: مدين 33.33 + 33.33 + 33.34، دائن 100. تحويل كل سطر منفردًا يعطي مدينًا 4812.34567891 مقابل دائن 4812.3456789 (فرق 0.00000001). بالتحويل كمجموعة: 1603.95481478 + 1603.95481478 + 1604.43604934 = **4812.3456789** = الدائن.
**مثال 2:** دائن بنك دولار 1000 USD × 48.5 = 48,500 · مدين بنك يورو 900 EUR × 53.9 = 48,510 ⇒ فرق 10 جنيه حقيقي؛ يُرفض الترحيل حتى يُضاف: دائن «فروق عملة» 10 EGP.

### 6.5 القيد العكسي
- من قيد مرحّل، غير معكوس، وليس عكسيًا؛ السبب إلزامي؛ صلاحية `journal.reverse`.
- السطور نفسها بطرفين متبادلين، **بالمبالغ الأصلية والأساسية والأسعار المحفوظة** (لا تحويل جديد) ⇒ الصافي صفر بالضبط بالعملتين.
- يُرحَّل فورًا برقم جديد من سلسلة `RV`؛ تاريخه تاريخ الأصل إن كانت فترته مفتوحة، وإلا تاريخ يختاره المستخدم في فترة مفتوحة.
- **رقم القيد الأصلي يبقى صادرًا ومحجوزًا**؛ العكس لا يحرر رقمًا ولا يعيد استخدامه.

**القيد العكسي وحسابات المراقبة (مراجعة 2، النقطة 1):**
حساب صار حساب مراقبة (`allow_manual_entry = 0`) أو عُطِّل أو تغيّرت سياسة مركز تكلفته **بعد** ترحيل القيد الأصلي يجب ألا يمنع تصحيح ذلك القيد. وفي الوقت نفسه يجب ألا يصبح «العكسي» طريقًا لقيد يدوي جديد على حساب مراقبة. التصميم:
1. **المستخدم لا يُدخل سطور العكسي.** طلب العكس يحمل التاريخ والسبب فقط (`POST /api/journal/:id/reverse {date, reason}`)؛ الخادم يولّد السطور من سطور الأصل المرحّلة المخزنة. لا يوجد مسار يقبل سطورًا لقيد من نوع `reversal`، ولا يمكن إنشاء مسودة عكسية.
2. **كل سطر عكسي مرتبط بسطر أصلي** `reverses_line_id`، و**trigger في القاعدة** يرفض السطر ما لم يكن مرآة تامة له: نفس الحساب ومركز التكلفة والعملة والسعر ومصدره، والمبالغ الأصلية والأساسية متبادلة الطرفين حرفيًا، وسطر الأصل ينتمي إلى القيد المذكور في `reverses_id` وهو مرحّل. كل سطر أصلي يُعكس مرة واحدة (`UNIQUE (reverses_line_id)`)، وعدد السطور مطابق (يُتحقق منه عند الترحيل).
3. **الإعفاء محصور** في: `allow_manual_entry`، وكون الحساب أو المركز نشطًا، وسياسة مركز التكلفة الحالية — لأنها كلها خصائص تغيّرت بعد الأصل. **لا إعفاء** من: الحساب تفصيلي (لا يمكن أصلًا تحويل حساب له حركات إلى تجميعي)، الفترة مفتوحة، نطاق الفرع، صلاحية `journal.reverse`، السبب، الاتزان.
4. **النتيجة:** القيد العكسي لا يستطيع إلا إلغاء أثر مرحّل سابق بالضبط؛ أي سطر على حساب مراقبة لم يكن في الأصل يُرفض من الخادم ومن القاعدة.
5. المستندات التفصيلية في المرحلة 4 (الفواتير، التحصيل) ترحّل إلى حسابات المراقبة عبر المحرك بـ `source_type` خاص بها؛ القيد اليومي اليدوي لا يملك هذا المسار.

**اكتمال القيد العكسي — تقابل تام واحد لواحد (مراجعة 3، النقطة 2):**
صحة كل سطر منفردًا لا تكفي؛ العكسي يجب أن يعكس **كل** سطور الأصل، كلًّا **مرة واحدة**، **ولا شيء غيرها**. تُفرض أربعة شروط معًا تكافئ رياضيًا التقابل التام:

| # | الشرط | أين يُفرض |
|---|---|---|
| C1 | كل سطر في القيد العكسي له `reverses_line_id` غير فارغ، وسطر الأصل ينتمي إلى `reverses_id` لهذا القيد نفسه، والسطر مرآة تامة له | trigger عند إضافة السطر |
| C2 | لا يتكرر سطر أصل داخل العكسي | `UNIQUE (entry_id, reverses_line_id)` |
| C3 | لا يبقى سطر أصل بلا مقابل: `NOT EXISTS` سطر في الأصل غير مُشار إليه من العكسي | trigger الترحيل `draft → posted` |
| C4 | عدد سطور العكسي = عدد سطور الأصل | trigger الترحيل `draft → posted` |

C1 + C2 ⇒ كل سطر عكسي يقابل سطر أصل مختلفًا (لا زيادة ولا تكرار)؛ C3 ⇒ لا نقص؛ C4 تأكيد صريح للعدد. والعكسي متزن تلقائيًا لأنه مرآة لقيد متزن، ويُعاد فحص الاتزان مع ذلك.

**التنفيذ في معاملة واحدة:** المحرك ينشئ القيد العكسي (`draft`) ويضيف سطوره ثم يرحّله، كلها داخل معاملة `BEGIN IMMEDIATE` واحدة. لا يوجد مسار API يُبقي عكسيًا مسودة، فلا تُرى حالة وسيطة. الخادم يفحص C1–C4 قبل الترحيل ليعطي رسالة واضحة، وtrigger الترحيل يفحصها مستقلًا في المعاملة نفسها (قبل كتابة الأستاذ).
**عكسي مسودة دخل بـ SQL مباشر** لا يحجز العكس الحقيقي: تفرّد `reverses_id` مفروض بفهرس جزئي على القيود **المرحّلة** فقط؛ وفحص السلامة يُبلغ عن أي مسودة عكسية.

### 6.6 الأرصدة الافتتاحية
**في المرحلة 3:**
- نوع `opening`، سلسلة `OB`، صلاحية `journal.opening`؛ تاريخه **أول يوم من أول سنة مالية** (أقدم سنة في النظام) فقط.
- يتزن بنفسه؛ الفرق غير المعروف يوجَّه صراحة لحساب «أرصدة افتتاحية» يظهر رصيده في الميزان؛ يجوز تقسيمه على عدة قيود (لكل فرع مثلًا).
- في الأستاذ: `entry_kind = 'opening'` لتمييزه في التقارير.

**عدم التكرار مع الأرصدة التفصيلية المستقبلية (العملاء والموردين والمخزون):**
- الحساب الذي ستديره وحدة تفصيلية يصبح **حساب مراقبة** بـ `allow_manual_entry = 0`، فلا يقبل قيدًا يدويًا ولا افتتاحيًا بعد ذلك.
- المرحلة 4 ستوفر طريقين، **والمحرك يدعمهما من الآن** لأن الأستاذ لا يعرف إلا `source_type`:
  - (أ) **إن كان للحساب رصيد افتتاحي مرحّل في الأستاذ** (أُدخل في المرحلة 3 قبل وجود العملاء): الأرصدة التفصيلية تُسجَّل كـ **تخصيص لا يُرحَّل** إلى الأستاذ، ويُشترط أن يساوي مجموعها رصيد حساب المراقبة في تاريخ الافتتاح **بالضبط**.
  - (ب) **إن لم يكن له رصيد**: الأرصدة التفصيلية تُرحَّل عبر المحرك (`source_type = 'party_opening'` أو `'stock_opening'`) مقابل حساب الأرصدة الافتتاحية.
- في الحالتين يوجد أثر واحد فقط في الأستاذ، وفحص المطابقة (الأستاذ = مجموع التفصيلي) يكشف أي خلل.

### 6.7 الإقفال السنوي — جاهزية المحرك
- `entry_type = 'closing'` و`entry_kind = 'closing'` موجودان في القاعدة من الآن، والخدمة ترفض إنشاءهما في المرحلة 3.
- `gl_entries.fiscal_year_id` يتيح حساب نتيجة السنة وإقفالها في المرحلة 4 دون تعديل الأستاذ.
- المرحلة 4 تضيف حالة السنة (مفتوحة/مقفلة) وقيد الإقفال إلى الأرباح المرحّلة؛ لا ترحيل مدمّر.

### 6.8 الأرصدة في التقارير
رصيد الحساب = مجموع حركاته بالمحرك العشري (`dec_sum`) لا SUM؛ التجميعي = مجموع فروعه عبر `path`؛ أول المدة = كل الحركة قبل تاريخ البداية.

### 6.9 التحقق من القيم العشرية (مراجعة 2، النقطة 2)
منع علامة السالب وحده لا يكفي (`'abc'` و`'1e5'` و`'01'` و`'1.50'` تمر منه). الضمان على ثلاث طبقات مستقلة:

| الطبقة | ما تفعله | ما تحمي منه |
|---|---|---|
| 1. الإدخال (API) | كل مبلغ وسعر نص (لا Number) يمر بـ `validator.decimal` ثم `decimal.commit` بسياسة العملة؛ الموجب بـ `decimal.gt(x, 0)`؛ رفض أي خانات زائدة عن الاعتماد (`TOO_PRECISE`) دون تقريب صامت | أخطاء المستخدم والطلبات المباشرة للخادم |
| 2. القاعدة (`CHECK`) | **الشكل القانوني الموجب كاملًا** لكل مبلغ وسعر غير صفري في `journal_lines` و`gl_entries`: يبدأ بـ `[1-9]` أو `0.`، أرقام ونقطة واحدة فقط، لا نقطة في النهاية، لا صفر زائد بعد الكسر، خانات الكسر ≤ دقة التخزين (8 للمبالغ، 12 للسعر)، والأرقام الصحيحة ≤ 20. و`'0'` مسموح فقط للطرف المقابل في السطر. (جُرِّب النمط على 31 حالة في قاعدة مؤقتة أثناء إعداد المقترح فطابق المحرك في كلها) | `INSERT`/`UPDATE` مباشر بـ SQL من خارج البرنامج |
| 3. المحرك عند الترحيل | المحرك **يعيد قراءة سطور المسودة من القاعدة** ويمرر كل قيمة بـ `decimal.fromStorage` (يرفض غير القانوني `CORRUPT_VALUE`) ثم يتحقق من الموجب والطرف الواحد ودقة الاعتماد، **قبل** أي حساب. لا يثق بما فحصه عند الحفظ | قيمة دخلت بتجاوز `CHECK` (مثلًا `PRAGMA ignore_check_constraints = ON` — **ثبت أثناء الإعداد أنه يتجاوز CHECK فعلًا**) أو خلل برمجي |
| + | trigger الاتزان عند `draft → posted` يحسب بـ `dec_sum`/`dec_cmp` (دوال المحرك المسجلة على اتصال البرنامج)؛ خارج البرنامج هذه الدوال غير موجودة فيفشل الترحيل المباشر (fail-closed). فحص سلامة الأستاذ يمرر كل قيمة في `gl_entries` بـ `fromStorage` | ترحيل يدوي مباشر في القاعدة، وكشف أي تلف لاحق |

**الحد الصريح:** من يملك صلاحية الكتابة على ملف القاعدة نفسه يستطيع حذف الـ triggers. الحماية هنا ضد أخطاء البرنامج والتعديل العارض بـ SQL، والكشف بفحص السلامة والنسخ الاحتياطية الموثّقة؛ ليست بديلًا عن حماية الملف على الجهاز.

## 7. ضوابط الفترات والسنوات والتحذيرات (القرار 8)

### 7.1 حالات الفترة المالية — تعريف قاطع (مراجعة 2، النقطة 3)

| | **مفتوحة** `open` | **مغلقة** `closed` | **مقفلة نهائيًا** `locked` |
|---|---|---|---|
| المعنى | فترة عمل جارية | توقف مؤقت للمراجعة (إغلاق عادي، قابل للتراجع) | اعتماد نهائي، **لا رجعة** |
| الترحيل فيها (عادي، افتتاحي، عكسي) | **مسموح** | **مرفوض** — لكل الأنواع بما فيها العكسي | **مرفوض** |
| عكس قيد مرحّل فيها | العكسي بتاريخ الأصل | العكسي يُؤرَّخ في فترة مفتوحة يختارها المستخدم | نفس المغلقة |

| الانتقال المباشر مفتوحة ← مقفلة | — | — | **غير مسموح**: القفل من المغلقة فقط |

| الحذف | مع سنتها فقط (قرار المرحلة 2 رقم 5) | لا | لا |

### 7.2 الضوابط

- **P2 يخص القفل النهائي فقط وبالتسلسل:** لا تنتقل فترة إلى «مقفلة» ما دامت **أي فترة سابقة لها** — في سنتها أو في سنة سابقة — غير مقفلة. نتيجة مباشرة: لا يمكن إعادة فتح فترة تقع قبل فترة مقفلة (لأنها مقفلة بالضرورة). يُفرض في الخادم وبـ trigger في القاعدة.
  **الثابت المحفوظ دائمًا:** «كل فترة مقفلة، كل ما قبلها مقفل».
  **الذرية (مراجعة 3، النقطة 3):**
  1. الخادم ينفذ قراءة الفترات السابقة وتغيير الحالة داخل **معاملة `BEGIN IMMEDIATE` واحدة** (قائمة في `changeStatus`)؛ القفل على القاعدة يؤخذ قبل القراءة، فلا يستطيع مستخدم آخر تغيير أي فترة بين الفحص والتحديث.
  2. **trigger `BEFORE UPDATE OF status` في القاعدة** يفحص الشرط نفسه داخل جملة التحديث ذاتها — حتى `UPDATE` مباشر من خارج البرنامج أو تحديث عدة فترات بجملة واحدة لا يكسر الثابت: إن عولجت فترة قبل سابقتها تُلغى الجملة كلها.
  3. trigger ثانٍ: الانتقال إلى `locked` من `closed` فقط (القاعدة الحالية تفرضه في الخادم؛ يُضاف في القاعدة).
  4. **محاولتان متزامنتان لقفل يناير وفبراير:** إن نُفذ يناير أولًا ⇒ فبراير يجد يناير مقفلًا فيُقفل؛ إن نُفذ فبراير أولًا ⇒ يُرفض `PERIOD_LOCK_SEQUENCE` ثم يُقفل يناير. في الحالتين **لا تنشأ أبدًا** فترة مقفلة قبلها فترة غير مقفلة. محاولة قفل فبراير مع إعادة فتح يناير بالتزامن: إعادة فتح يناير تُرفض إن سبقها قفل فبراير؛ وإن سبقته فقفل فبراير يُرفض.
- **P3 يخص الإغلاق العادي فقط وهو تحذير:** إغلاق فترة وقبلها فترة مفتوحة مسموح (قد تُراجع فترة قبل أخرى) لكن الرد والواجهة يعرضان تحذيرًا بأسماء الفترات المفتوحة السابقة. لا يمنع شيئًا.

| # | الضابط | النوع |
|---|---|---|
| P1 | الترحيل في فترة مغلقة أو مقفلة أو خارج السنوات المعرّفة | **منع** (قائم من المرحلة 2) |
| P2 | **القفل النهائي بالتسلسل:** لا تُقفل فترة ما دامت أي فترة سابقة لها (عبر السنوات) غير مقفلة | **منع** (جديد؛ خادم + قاعدة) |

### 7.3 نهائية التقارير
كل تقرير يرد بحقل `finality = { final, reasons[] }`، والواجهة والطباعة والتصدير تختم «غير نهائي» مع الأسباب:
- **نهائي** فقط إذا: كل الفترات في نطاق التقرير **مقفلة نهائيًا**، **و** لا توجد سنة مالية سابقة لنطاق التقرير (لأن إقفال السنوات غير متاح قبل المرحلة 4).
- لذلك في المرحلة 3: **أي تقرير يمس سنة لاحقة لأول سنة يكون «غير نهائي» دائمًا** بسبب `PRIOR_YEAR_NOT_CLOSED`، ويوضح الميزان أن أرصدة أول المدة لحسابات الإيرادات والمصروفات تتضمن نتائج سنوات لم تُقفل.
- أسباب أخرى: `PERIOD_OPEN` (فترة مفتوحة في النطاق)، `PERIOD_NOT_LOCKED` (فترة مغلقة غير مقفلة).

## 8. الترقيم المتزامن — آلية الضمان

1. إصدار الرقم **داخل معاملة الترحيل نفسها**، والمعاملات تبدأ بـ `BEGIN IMMEDIATE` (قائم في `core/db.js`) ⇒ قفل الكتابة من أول لحظة؛ المستخدم الثاني ينتظر (`busy_timeout = 5000`) ثم يقرأ العداد المحدَّث.
2. better-sqlite3 متزامنة: المعاملة لا يتخللها طلب آخر في نفس العملية.
3. الزيادة جملة واحدة: `INSERT … ON CONFLICT DO UPDATE SET last_value = last_value + 1 RETURNING last_value`.
4. خطوط دفاع في القاعدة: `issued_numbers.number UNIQUE` (كل المستندات)، `UNIQUE (series, branch_key, year_key, seq)`، `journal_entries.number UNIQUE`، trigger الزيادة بواحد فقط ومنع الحذف ⇒ أي خلل = رفض المعاملة كلها، لا رقم مكرر.
5. لا فجوات: فشل الترحيل يلغي زيادة العداد مع كل شيء.
6. لا إعادة استخدام: الرقم يدخل `issued_numbers` (إضافة فقط) لحظة الترحيل؛ العكس يأخذ رقمًا جديدًا؛ إغلاق السنة لا يمس العدادات؛ إعدادات السلسلة مقفلة بعد أول رقم، وحتى لو أُنشئت سلسلة جديدة بنفس البادئة فإن تفرّد `number` في `issued_numbers` يمنع أي تكرار.
7. التشغيل على الشبكة مستقبلًا بأكثر من عملية: قفل SQLite على مستوى الملف يبقي الضمان نفسه.

### 8.1 إعدادات السلسلة بعد أول إصدار (مراجعة 3، النقطة 4)
«الإصدار» = وجود أي صف في `issued_numbers` لهذه السلسلة.

### 8.2 مواصفات اختبار التزامن (مراجعة 3، النقطة 5)
- **البيئة:** 4 عمليات Node **منفصلة** (`child_process.fork`)، لكل منها اتصالها الخاص بنفس ملف القاعدة عبر `openDatabase` (WAL، `busy_timeout = 5000`). تبدأ معًا عند إشارة واحدة.
- **العمل:** كل عملية تنفذ 250 محاولة إصدار في سلسلة واحدة لنفس (الفرع، السنة)، كل محاولة في معاملة `BEGIN IMMEDIATE`؛ **10% منها فشل متعمد** يُرمى بعد الإصدار داخل المعاملة (لإثبات أن الإلغاء يعيد العداد).
- **سياسة `SQLITE_BUSY`:** `busy_timeout` ينتظر حتى 5 ثوانٍ داخليًا. إن انتهى وظهر `SQLITE_BUSY`: **حتى 5 إعادات** للمحاولة نفسها بانتظار 50، 100، 200، 400، 800 ملّي ثانية (+ عشوائي ≤ 25). أقصى انتظار للمحاولة الواحدة ≈ 6 × 5 ث + 1.6 ث ≈ 31.6 ث. كل إعادة تُعدّ وتُسجَّل (العملية، رقم المحاولة، الزمن). **استنفاد الإعادات = فشل للاختبار**، لا يُتجاهل.
- **أي خطأ آخر** غير الفشل المتعمد و`SQLITE_BUSY` (مثل `SQLITE_CONSTRAINT`) ⇒ **فشل فوري للاختبار** مع الخطأ كاملًا.
- **تقرير كل عملية:** الأرقام التي نجحت، عدد الفشل المتعمد، عدد إعادات BUSY، عدد الاستنفاد.
- **شروط النجاح (كلها معًا):**
  1. مجموع النجاحات في التقارير = عدد صفوف `issued_numbers` = `last_value` = N.
  2. التسلسلات = {1 … N} بالضبط: لا تكرار ولا فجوة.
  3. اتحاد الأرقام المُبلغ عنها = الأرقام في القاعدة، ولا رقم مُبلغ عنه مرتين.
  4. لا أثر لأي محاولة فشل متعمد (لا صف ولا زيادة عداد).
  5. صفر استنفاد إعادات، صفر أخطاء غير معالجة، وكل العمليات خرجت بالرمز 0.
  6. `integrity_check = ok` و`foreign_key_check` فارغ.
- **التوثيق:** يُسجَّل في `PHASE3_REPORT.md`: N، عدد الفشل المتعمد، عدد إعادات BUSY لكل عملية، أطول انتظار، الزمن الكلي، والنتيجة. **النتيجة لا يمكن ذكرها الآن** لأن الاختبار لم يُنفذ.
- **الاستخدام نفسه** لاختبار تزامن P2 (القسم 12، 3.2) بنفس سياسة BUSY وشروط فشل مماثلة.

## 11. الواجهة

- **شاشة القيد:** رأس (التاريخ، الفرع، العملة الافتراضية، البيان، المرجع) + جدول سطور بلوحة المفاتيح: الحساب، مركز التكلفة، البيان، العملة (افتراضيًا عملة الرأس)، السعر (من الجدول؛ يصبح قابلًا للتعديل فقط مع الصلاحية ويطلب السبب)، مدين، دائن. Enter ينتقل للخلية التالية ويضيف سطرًا في النهاية؛ Ctrl+S حفظ مسودة؛ اختصار مستقل للترحيل مع تأكيد.
- **المجاميع:** من الخادم (`POST /api/journal/preview`) — الواجهة لا تحسب أي مبلغ: المجاميع لكل عملة، المقابل الأساسي لكل سطر، المدين والدائن الأساسي، **الفرق**. الترحيل معطل ما دام الفرق ≠ 0، والخادم يتحقق مستقلًا.
- **دفتر اليومية، كشف الحساب، ميزان المراجعة:** تصفية بالتاريخ والفرع ومركز التكلفة؛ شريط «غير نهائي» بالأسباب؛ الانتقال من الميزان إلى الكشف ومن الكشف إلى القيد؛ طباعة وتصدير Excel بالختم نفسه.
- عربي/إنجليزي، RTL/LTR، والهاتف بلا تمرير أفقي للصفحة.
